# Plan: December 2026 – May 2027

[Back to the roadmap](roadmap.md) · [App 1.0 plan](app-plan.md) · [Project review](project-review.md) · [UI audit](ui-audit-2026-11-20.md)

Written 2026-11-20 from an audit of the roadmap, the code and the issue and PR
history, with independent input from two other reviewers (GPT-6.2 Sol and
Gemini 4 Neon). All three reached the same main conclusions. Where they
disagreed, the decision and its reason are recorded under
[Reviewer disagreements](#reviewer-disagreements).

This is a proposal. Items marked **needs decision** wait for the maintainer.
Everything else becomes a GitHub issue before work starts, so the
[agent rules](roadmap.md#for-agents) still apply: one issue at a time, scoped
by its acceptance checkboxes.

## Summary

For six months, work on three things a Canadian investor would notice:
**tax and contribution-room figures they can reconcile, data they can recover
safely, and a Mac release they can trust when they install it.**
Stop adding CLI report combinations until those are done.

| Window | Theme | Release |
| --- | --- | --- |
| Dec 2026 | 1. Ship what's on `main` and close safety gaps | 3.2.0 |
| Jan – mid Feb 2027 | 2. Tax and contribution-room correctness, before tax slips arrive | 3.3.0 |
| Feb – Mar 2027 | 3. Mac app parity and resilience | 3.4.0 |
| Mar – Apr 2027 | 4. Trust in the release and a verified QA pass | 3.4.x |
| Apr – May 2027 | 5. Broker imports driven by real exports, and walkthroughs with users | 3.5.0 |

Tax season shapes the timing. T4/T5/T3/T5008 slips arrive in February and
March, and returns are due on 2027-04-30, so tax fixes must be released by mid
February, while people are reconciling against their slips.

## Audit findings

### The roadmap page is stale

- **Status** still says to "follow #169 for release status". 3.1.0 was published
  on 2026-11-19 and #169 is closed.
- **Unreleased work isn't on it.** `main` has 15 commits since 3.1.0, including
  two schema migrations (automation history, schema version 2, #180; the
  foreign-property flag, schema version 3, #179), backup restore preview
  (#171, #173), `backup verify --all` (#176), the T1135 estimate (#179) and
  privacy fixes (#186). A 3.1.0 install can't open a ledger that a newer build
  has migrated, so 3.2.0 needs an upgrade and rollback rehearsal.
- **The Done table** stops at #149 and says 57 datasets. `report` now has 64
  (#191).

### There's nothing in Next, so bulk feature batches filled the gap

"Choose further work from what people run into" assumes a channel for that
input. There's no feedback channel: of the 78 issues ever filed, the owner filed
65 and a bot filed 13, and #25 (Later) is the only open issue. The gap has gone to
combinatorial CLI work. About 25 of the last 60 merged PRs are "N improvements"
or "N capabilities" batches. `docs/` holds 78 inventory files for them (about
5,300 lines). `cli/` has grown to roughly 18k lines, against about 6k for the
core engine modules (`models`, `ledger`, `valuation`, `tax`, `analytics`,
`services`, `csvio`, `brokers`, `db`, `market`). Each option adds compatibility and documentation obligations, but few
workflows have been verified end to end.

## Themes

### 1. Ship what's on `main` and close safety gaps (December 2026) → 3.2.0

- Refresh `docs/roadmap.md` (done in this change) and file the issues in this
  plan, with `agent-ready` or `needs-decision` labels.
- Rehearse an upgrade from 3.1.0 to 3.2.0 and a rollback on a fictional ledger.
  3.1.0 can't open a migrated ledger, so its in-place `backup restore` isn't a
  rollback path. Restore the pre-upgrade backup with 3.1.0 into a separate data
  directory (`MARKETPULSE_DATA`) and compare balances, history and tax output
  there. Document the live rollback separately: with the app closed, copy the
  pre-upgrade backup over the ledger file.
- Restore confirmation also checks the live ledger's revision. If the ledger
  changed after the preview, ask for a new preview, the way CSV import already
  does.
- Create the data directory with `0700`, and the database, WAL files and backups
  with `0600`. Tighten existing files on startup.
- Add the 2027 TFSA limit once CRA publishes it (usually late November). Don't
  guess the amount.
- Release 3.2.0 and run the full [QA checklist](qa.md) on the release build.
  Report items that weren't run as UNVERIFIED.

**Done when:** 3.2.0 is published, the rollback rehearsal is recorded on its
issue, and a restore after a concurrent edit is refused with a request to
preview again.

### 2. Tax and contribution-room correctness (January to mid February 2027) → 3.3.0

Every change here touches financial math, so each needs its own issue with
before-and-after tests on fictional fixtures ([rules](../AGENTS.md#rules)).

- **Fixtures first.** Add independently worked examples of pooled CAD/USD ACB,
  missing FX, superficial losses across a year boundary and across a split,
  transfers between accounts, return of capital above ACB, and T3
  adjustments. Write them before changing code, so each fix shows which result
  was wrong.
- **Contribution room:** convert foreign-currency contributions at the
  trade-date rate, and count in-kind contributions (transfers from a
  non-registered account) at fair market value. Direct transfers between two
  of the holder's registered accounts of the same kind, such as TFSA to TFSA,
  aren't contributions. A buy inside a registered account isn't a
  contribution either, since it may be funded by a sale. In an account that
  doesn't track cash, a buy's funding source is unknown even when other
  contributions are recorded, so room there counts only recorded
  contributions and is marked as possibly incomplete. Show which flows were
  counted.
- **Phantom distributions:** add a way to record an adjustment that raises
  ACB: a non-cash (phantom) distribution or a negative T3 box 42 amount. Keep
  return of capital (positive box 42) on `ROC`, which lowers ACB. A new transaction type, or an amount type on an existing one,
  is decided in its issue. A new `TxnType` must also be handled in `_apply`,
  `analytics.external_flows` and the TUI `TransactionForm`, as the
  [architecture notes](../AGENTS.md#architecture) require.
- **Identical property:** let the user link symbols into one ACB pool.
- **Superficial loss across a split:** confirm with a fixture, then fix.
- **T1135:** review it against CRA guidance, including foreign cash, Canadian
  issuers listed in the US, the peak during each day, and any thresholds enacted
  for 2027.
- **Per-trade FX override:** let a user enter the rate their broker actually
  used. It works offline and helps more than a second FX source.

**Done when:** the fixtures pass, the CLI, TUI, Mac app and tax CSV agree
wherever they show the same figure, and any total that's incomplete or uses an
unsupported case says so where the user reads it. Release by mid February.

### 3. Mac app parity and resilience (February to March 2027) → 3.4.0

- Show the T1135 status in the Mac Tax workspace, and the per-asset foreign
  setting in Assets.
- Show automation history and `backup verify --all` results in Automation.
- Handle failed storage writes on every Mac write path, with the same
  retry pattern as transaction save.
- Prevent concurrent automation runs from sending duplicate alerts, using a
  cross-process lock around `automation.run_cycle`.
- Split `DesktopViews.swift` (about 2,000 lines) by workspace, without
  changing behaviour.
- A narrower minimum window than 980 points is optional this cycle.

**Done when:** every engine feature since 3.1.0 that a Mac user needs is in
the app, the bridge check covers it, and two processes running automation at
once send each alert only once.

### 4. Trust in the release (March to April 2027)

- **Needs decision: Developer ID signing and notarization.** Today every DMG
  download, including each update, shows a Gatekeeper malware warning and
  needs **Open Anyway** on macOS 15 and later. That's hard to ask of
  investors who don't use a terminal. Notarization needs an Apple Developer
  membership (check Apple's current price). Only notarization removes the
  warning. A Homebrew cask doesn't: Homebrew quarantines the download, so
  Gatekeeper still blocks an unnotarized app on first open. If the maintainer
  declines again, keep the **Open Anyway** steps in the install guide, and say
  there that installing needs some technical comfort.
- Add GitHub artifact attestations to `release.yml`, so `SHA256SUMS` isn't the
  only check, and it isn't served from the same release as the files it checks.
- Before a release, walk through a release candidate on clean Apple silicon and
  Intel user accounts: browser download, first launch, upgrade over existing
  data, onboarding, menu bar, Dock, and spoken VoiceOver (reopening the scope
  of #47 as a smaller issue).
- Write the threat-model ADR for #25: what file permissions, encryption or
  keychain unlock would protect, and backups and exports in particular.
  Building encryption stays in Later.

**Done when:** a release has a complete QA table with no UNVERIFIED items on
install, upgrade or restore, its artifacts are attested, and the #25 ADR is
merged.

### 5. Imports and feedback from real users (April to May 2027) → 3.5.0

- Add a feedback channel: an issue template for import, tax-mismatch and install
  reports, linked from the app's About screen and the README. Nothing is sent
  automatically.
- Choose which broker profiles to add (TD Direct Investing, RBC Direct Investing,
  NBDB and IBKR are the likely candidates) from requests and anonymized sample
  headers, with fictional fixtures. Handle withholding tax and FX conversion rows,
  and explain each skipped row and how to record it by hand.
- Have a few users walk through a fictional ledger, from a broker CSV to
  reconciling and exporting tax, then restoring a backup. Fix whatever stops
  them.
- Measure save-to-visible time on representative Macs before reopening a
  persistent backend (#48).

**Done when:** at least two new profiles pass import and preview tests on
fictional fixtures, and participants can finish the walkthrough without help.

## Stop, de-prioritize, keep

- **Stop** "N improvements" and "N capabilities" batches. `report` and
  `summarize` are in maintenance only: fix bugs, add nothing. New CLI
  options need an issue that names the workflow they serve.
- **Stop** counting progress in feature combinations. Count user workflows
  verified end to end and QA items passing on a release build.
- **De-prioritize** new TUI shortcuts, a persistent backend (#48) until native
  timings justify it, and any sync or mobile work.
- **Keep** Windows dropped ([ADR 0002](adr/0002-no-windows-build.md)). Both
  reviewers agreed.
- **Keep** encryption (#25) in Later, but ship file permissions in Theme 1 and
  the threat-model ADR in Theme 4.

## Reviewer disagreements

- **FX source.** Neon proposed optional Bank of Canada rates. This plan adds a
  per-trade override instead: it uses the rate the broker actually charged and
  needs no new network calls, which the [rules](../AGENTS.md#rules) don't allow
  without an issue that calls for them.
- **QA target for December.** Neon set 26 of 28 items passing for 3.2.0. This
  plan requires a complete table with any UNVERIFIED items explained in
  December, and no UNVERIFIED install, upgrade or restore items by Theme 4,
  because the clean-account checks need a separate macOS user and real
  download conditions.
- **Narrow windows.** Neon included the 980-point minimum width in Mac parity.
  It's optional here: it needs Overview, the filter bars and the fixed-width
  tables redesigned together, and it doesn't affect correctness.
- **Notarization.** Sol asked for a maintainer decision. Neon recommended
  notarizing. This plan recommends it and lists it as a decision, since the
  maintainer chose ad-hoc signing on purpose in the [App 1.0 plan](app-plan.md).
